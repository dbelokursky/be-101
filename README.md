# BE-101 — Бэкенд для смежных специальностей

Интерактивный курс для фронтендеров, QA-инженеров и аналитиков продуктовой команды:
учимся понимать бэкенд и писать код на стеке **Spring Boot, Hibernate, Kafka, Lombok, MapStruct, Actuator/Micrometer**.

## Как открыть курс

Курс — статический сайт, сервер не нужен:

1. Склонируй репозиторий
2. Открой файл `site/index.html` двойным кликом в браузере

Прогресс хранится локально в твоём браузере (localStorage) — никуда не отправляется.

> **Онлайн-версия**: <https://dbelokursky.github.io/be-101/> — сайт деплоится
> автоматически при изменении `site/` в `main` (воркфлоу `.github/workflows/deploy-pages.yml`).

## Как учиться

- Уроки читаются в любом порядке, но лучше по порядку 🙂
- После каждого урока — квиз: отвечаешь, сразу видишь пояснение «почему»
- Урок считается пройденным (✓), когда квиз сдан на **80%+**. Пересдавать можно сколько угодно
- К некоторым урокам прилагается **лабораторная** — настоящий код в этом же репозитории

## Как делать лабораторные

Для лабораторных нужны JDK 21 и Maven. Проверь окружение по [README лабы 0](https://github.com/dbelokursky/be-101/blob/lab-0/README.md). Карточка каждой лабы ведёт к инструкции в ветке задания и к эталону, если он есть.

| Лаба | Как проверить |
|---|---|
| `lab-0` | `mvn test` проходит, запущенное приложение отвечает на `GET /api/ping` |
| `lab-1` | Проверь примеры запросов из README и сверись с `lab-1-solution` |
| `lab-2`–`lab-10` | В исходной ветке есть падающие проверки. Лаба сдана, когда `mvn test` проходит целиком |

Открой нужную ветку и прочитай её README. Например, для лабы 2 начни с первого прогона.

```bash
git switch lab-2
mvn test
```

После выполнения снова запусти проверку. Сравнить подход можно в ветке `lab-N-solution`.

### Проверка в GitHub Actions

Для лаб 2–10 можно проверить решение в своём форке.

1. Создай форк и открой его вкладку **Actions**. Включи workflows, если GitHub предлагает это сделать. Если хочешь клонировать сам форк, при его создании скопируй ветки лабораторных.
2. Если ты клонировал исходный репозиторий, добавь форк как второй remote. Замени `YOUR-LOGIN` на свой логин GitHub.

   ```bash
   git remote add fork https://github.com/YOUR-LOGIN/be-101.git
   ```

3. Закоммить изменения в ветке задания и отправь их в одноимённую ветку форка, например `git push fork lab-2`. Если клонировал сам форк, используй `origin` вместо `fork`.
4. Во вкладке **Actions** форка открой запуск **Lab check** для своего коммита. Красный запуск показывает, какие проверки ещё падают. Зелёный означает, что `mvn -B test` прошёл.

## Структура репозитория

```
content/            # уроки курса (markdown + квизы)
  module-1/         # «Spring Boot: бэкенд с нуля»
site/               # сгенерированный сайт курса (открывать site/index.html)
tools/generator/    # генератор статики из markdown
```

## Пересобрать сайт после правки уроков

```bash
cd tools/generator
npm install         # один раз
npm run build       # пересоберёт site/
```

## Разработка (для мейнтейнеров)

Интеграционная ветка — `develop`: каждый урок делается в отдельной ветке
(`lesson-02`, `lesson-03`, …) и мержится в `develop` после готовности.

```bash
git checkout develop
git checkout -b lesson-02
# … пишем content/module-1/lesson-02.md, npm run build …
git checkout develop
git merge lesson-02
```

После правки уроков пересобери сайт: `cd tools/generator && npm run build` —
и закоммить обновлённый `site/` вместе с контентом.

Ветки лаб (`lab-N`, `lab-N-solution`) в мерж-процесс не входят — это
задания для студентов, они живут отдельно.

При изменении `.github/workflows/lab-check.yml` обнови копии в ветках `lab-2`–`lab-10` и соответствующих ветках решений. При пуше GitHub запускает файл из коммита ветки. В заготовках ожидаются красные проверки, в эталонах — зелёные.
