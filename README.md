# Лаба 10. Выпускной проект Spring

Сервис уже принимает и сохраняет заказы. Запусти приёмку, найди, где расходятся заказ, событие и метрика при сбое, затем исправь запись и публикацию с помощью transactional outbox.

## Первый прогон

Понадобятся JDK 21 и Maven. Приёмник сам запускает H2 и Kafka.

```bash
git switch lab-10
mvn test
```

Проверки обычного создания, чтения, события, метрики, валидации и health проходят. Три проверки надёжности начинают с красного результата.

| Проверка | Что обнаружит в заготовке |
| --- | --- |
| `rollback_leavesNoOrderOutboxEventOrMetric` | Заказ откатился, но в Kafka есть его событие и счётчик вырос |
| `kafkaFailure_keepsPendingEventAndRetriesAfterRecovery` | Заказ сохранён, а записи, которую можно отправить после сбоя, нет |
| `lostAck_retriesWithTheSameEventId` | Без записи outbox повторная попытка с тем же `eventId` невозможна |

Открой `OrderService.create`. Найди, где сохраняется заказ, запускается отправка и растёт счётчик. Когда Spring фиксирует транзакцию БД? Что произойдёт, если Kafka подтвердит отправку до отката? Где останется информация для повтора, если отправка завершится ошибкой? Сверь вывод с [разбором dual-write](https://dbelokursky.github.io/be-101/#/m4-lesson-03).

## Контракт на время задания

| Запрос | Ответ |
| --- | --- |
| `POST /api/orders` с телом `{"customer":"ann","amount":"1990"}` | `201` после сохранения, поля `id`, `customer`, `amount`, `status: "NEW"` |
| `GET /api/orders` | `200` и список заказов |
| Создание с пустым `customer` или отрицательным `amount` | `400` |
| `GET /actuator/health` | `UP` |

Публикуется `OrderCreatedEvent` в `orders.created`. Ключ Kafka — строковый `id` заказа. `eventId` идентифицирует событие и используется при повторе. Метрика `orders.created.total` должна увеличиться на один после успешного коммита заказа.

## Что изменить

1. В `OrderService.create` записывай заказ и строку `order_outbox` в одной транзакции БД. Миграция, сущность и репозиторий уже есть. У строки есть собственный `eventId` и поля для события.
2. Увеличивай счётчик после коммита транзакции. Проверь дельту метрики и состояние обеих таблиц при откате.
3. Реализуй `OrderOutboxPublisher.publishNext`. В отдельной транзакции возьми одну ожидающую строку с блокировкой. Отправь событие, дождись подтверждения брокера и только тогда выставь `published_at`. При ошибке следующая попытка должна взять ту же запись и тот же `eventId`. Учти, что таймаут возможен и после записи сообщения в Kafka.
4. Повтори `mvn test`. Все девять проверок должны пройти. Сверь обработку повторной доставки с [уроком про outbox и идемпотентность](https://dbelokursky.github.io/be-101/#/m4-lesson-05).

Приёмник выключает планировщик и вызывает `publishNext` в нужный момент. В тесте сбоя продюсер сначала возвращает ошибку, затем снова отправляет в Kafka. Проверка потерянного подтверждения отправляет в брокер две записи и сравнивает их `eventId`.
