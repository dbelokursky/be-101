# Расследование 504 при отмене заказа

Анна нажала «Отменить заказ». Браузер получил `504`. Разбери сохранённые артефакты по порядку. Сначала определи, где искать результат операции. Затем подтверди его по данным и реши, как повторить запрос.

## Запрос в браузере

Во фрагменте **Network** от 16 января все отметки времени указаны в UTC.

```http
POST /api/orders/42/cancel HTTP/1.1
Host: api.shop.example.test
Authorization: Bearer demo-anna
Idempotency-Key: cancel-42-1

HTTP/1.1 504 Gateway Timeout
X-Trace-Id: 42c0a600000000000000000000000001
```

`504` означает, что шлюз вовремя не получил ответ от сервиса, к которому обратился. Чтобы узнать результат самой операции, проследи запрос дальше шлюза. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.5)

```case
title: "Выбери следующий шаг расследования"
task: >
  Запиши, что подтверждает ответ 504 и какие исходы операции пока возможны.
  Назови следующий источник данных. По какому полю найдёшь именно этот запрос?
placeholder: "Что уже известно\nГипотеза\nГде и по какому полю её проверить"
reference: |
  Шлюз ожидал ответ две секунды. Найди трейс по `X-Trace-Id`. В нём видно, что сервис принял запрос, зафиксировал отмену и сформировал ответ уже после таймаута шлюза.

      traceId=42c0a600000000000000000000000001
      11:59:52.000Z gateway POST /api/orders/42/cancel deadline=11:59:54.000Z
      11:59:52.012Z orders  start key=cancel-42-1 orderId=42
      11:59:52.180Z orders  tx.commit tx=tx-cancel-42 status=CANCELLED bonusId=refund-42
      11:59:54.000Z gateway upstream_timeout status=504
      11:59:54.280Z orders  response_ready status=204

  Спан шлюза объясняет, откуда взялся HTTP-ответ. Запись `tx.commit` с тем же `traceId` свидетельствует о сохранённой отмене. Дальше можно сверить её с состоянием заказа и записью возврата.
```

## Состояние заказа и повтор запроса

```case
title: "Проверь результат отмены и составь баг-репорт"
task: >
  Сверься с трейсом из предыдущего блока. Назови два наблюдения в БД,
  которые подтвердят, что операция состоялась. Анна повторяет запрос в 12:00:03Z,
  после истечения окна отмены. Какой ключ она должна отправить и чего ждать?
  Запиши короткий баг-репорт с запросом, ожиданием, фактом, traceId и следующим шагом.
placeholder: "Как проверю БД\nЧто отправит клиент\nКороткий баг-репорт"
reference: |
  В срезе на `11:59:53Z` обнаруживаются обе записи.

  | Источник | Наблюдение |
  | --- | --- |
  | `orders` | `id=42`, `status=CANCELLED`, `cancelled_at=2026-01-16T11:59:52.180Z` |
  | `bonus_transactions` | Одна строка `refund-42` для `order_id=42` с причиной `ORDER_CANCELLED` и суммой `+120` |

  При повторе сервис использует сохранённый результат по ключу `cancel-42-1`. По [контракту](#/m2-order-cancellation-review) он возвращает его даже после истечения окна.

      12:00:03.000Z POST /api/orders/42/cancel Idempotency-Key=cancel-42-1
      12:00:03.019Z orders replay key=cancel-42-1 status=204
      12:00:03.100Z GET /api/orders/42 -> 200 {"id":42,"status":"CANCELLED"}
      12:00:03.130Z bonus_transactions(order_id=42,reason=ORDER_CANCELLED) -> [refund-42]

  Повтор вернул `204`. Заказ остался в `CANCELLED`, и возврат остался один.

  ### Пример баг-репорта

  **После сохранённой отмены браузер получил 504.** Запрос `POST /api/orders/42/cancel` с ключом `cancel-42-1`. Ожидали `204` по завершении операции. Получили `504` при таймауте шлюза. Трейс `42c0a600000000000000000000000001` показывает коммит в `11:59:52.180Z` и готовность ответа в `11:59:54.280Z`. Следующий шаг — проверить, где сервис потратил время между коммитом и подготовкой ответа. Тот же ключ уже вернул `204`. По заказу есть один возврат.
```

## 504 и неполные данные

Анна отменяет другой заказ, `58`. Она создала его 15 января в `14:00:00Z`. По [контракту отмены](#/m2-order-cancellation-review) окно закрывается 16 января в `14:00:00Z`. В браузере доступен такой обмен.

```http
POST /api/orders/58/cancel HTTP/1.1
Host: api.shop.example.test
Authorization: Bearer demo-anna
Idempotency-Key: cancel-58-1

HTTP/1.1 504 Gateway Timeout
X-Trace-Id: 58c0a600000000000000000000000003
```

В выгрузку трейса попали три записи.

```text
traceId=58c0a600000000000000000000000003
13:59:57.900Z gateway POST /api/orders/58/cancel deadline=13:59:59.900Z
13:59:57.914Z orders  start orderId=58 key=cancel-58-1
13:59:59.900Z gateway upstream_timeout status=504
```

У дежурного пока есть срез основной БД на `13:59:50.000Z`.

| Источник | Данные |
| --- | --- |
| `orders` | `id=58`, `status=NEW` |
| `bonus_transactions` | Для заказа `58` нет строк с причиной `ORDER_CANCELLED` |

```case
title: "Реши, каких свидетельств не хватает"
task: >
  Запиши, что известно о запросе по Network и трейсу. На какой вопрос отвечает
  срез БД с учётом его времени? Какие сведения ты запросишь, чтобы узнать
  состояние заказа и результат попытки с ключом cancel-58-1?
  Укажи источник и идентификаторы, по которым искать каждое свидетельство.
placeholder: "Подтверждённые факты\nЧто показывает срез и на какой момент\nКакие данные запрошу и по каким идентификаторам"
reference: |
  Шлюз вернул `504`, а запись `orders start` подтверждает, что сервис начал обработку. Срез показывает `NEW` и ноль возвратов до запроса. На этом этапе результат отмены неизвестен.

  Запроси свежий срез основной БД по `orderId=58` и строки журнала бонусов с причиной `ORDER_CANCELLED`. Для исходной попытки ищи записи сервиса по `traceId=58c0a600000000000000000000000003` или результат по сочетанию `anna`, `58`, `cancel-58-1`.

  ### Что нашли в 14:00:02Z

  | Источник | Наблюдение |
  | --- | --- |
  | Свежий срез `orders` | `id=58`, `status=CANCELLED`, `cancelled_at=13:59:59.120Z` |
  | Свежий срез `bonus_transactions` | Одна строка `refund-58` для `order_id=58` с причиной `ORDER_CANCELLED`, созданная в `13:59:59.120Z` |
  | Журнал сервиса | В `13:59:59.120Z` коммит отмены для `orderId=58`, пользователя `anna` и ключа `cancel-58-2` из второй вкладки |
  | Результат по ключу | Для `anna`, `58`, `cancel-58-2` сохранён `204`. Для `anna`, `58`, `cancel-58-1` успешного результата нет |
```

```case

task: >
  Открой свежие данные в разборе выше. Какой результат можно показать Анне?
  Какой запрос записал отмену и возврат? Нужен ли новый POST для завершения
  действия в интерфейсе? Укажи ответ при диагностическом повторе исходного
  запроса по учебному контракту и проверку числа возвратов.
placeholder: "Итог по заказу и свидетельства\nКакая попытка записала отмену\nРешение для интерфейса\nЕсли всё же повторить исходный запрос"
reference: |
  Свежий срез подтверждает статус `CANCELLED` и один возврат `refund-58`. По записи коммита и сохранённому ответу видно, что отмену выполнил запрос с ключом `cancel-58-2`. Этот `204` относится ко второй вкладке.

  Чтобы выяснить, чем завершился первый вызов внутри сервиса, запроси запись завершения по его исходному `traceId`.

  Покажи Анне отменённый заказ по свежему состоянию. Для завершения действия в интерфейсе достаточно подтверждённого `CANCELLED`.

  Если для диагностики повторить исходный запрос с `cancel-58-1`, API сначала поищет успешный результат именно по этому ключу. Его нет, поэтому сработает проверка состояния заказа и сервис вернёт `409 ORDER_ALREADY_CANCELLED`. Проверь, что для заказа `58` и причины `ORDER_CANCELLED` по-прежнему существует ровно одна строка `refund-58`.
```
