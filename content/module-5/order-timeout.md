# Расследование 504 при отмене заказа

Анна нажала «Отменить заказ». Браузер получил `504`. Разбери сохранённые артефакты по порядку. Сначала определи, где искать результат операции. Затем подтверди его по данным и реши, как повторить запрос.

## Запрос в браузере

Во фрагменте **Network** от 16 января все отметки времени указаны в UTC.

```http
POST /api/orders/42/cancel HTTP/1.1
Host: api.shop.example.test
Authorization: Bearer demo-anna
Idempotency-Key: cancel-42-1

HTTP/1.1 504 Gateway Timeout
X-Trace-Id: 42c0a600000000000000000000000001
```

`504` означает, что шлюз вовремя не получил ответ от сервиса, к которому обратился. Чтобы узнать результат самой операции, проследи запрос дальше шлюза. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.5)

```case
title: "Выбери следующий шаг расследования"
task: >
  Запиши, что подтверждает ответ 504 и какие исходы операции пока возможны.
  Назови следующий источник данных. По какому полю найдёшь именно этот запрос?
placeholder: "Что уже известно\nГипотеза\nГде и по какому полю её проверить"
reference: |
  Шлюз ожидал ответ две секунды. Найди трейс по `X-Trace-Id`. В нём видно, что сервис принял запрос, зафиксировал отмену и сформировал ответ уже после таймаута шлюза.

      traceId=42c0a600000000000000000000000001
      11:59:52.000Z gateway POST /api/orders/42/cancel deadline=11:59:54.000Z
      11:59:52.012Z orders  start key=cancel-42-1 orderId=42
      11:59:52.180Z orders  tx.commit tx=tx-cancel-42 status=CANCELLED bonusId=refund-42
      11:59:54.000Z gateway upstream_timeout status=504
      11:59:54.280Z orders  response_ready status=204

  Спан шлюза объясняет, откуда взялся HTTP-ответ. Запись `tx.commit` с тем же `traceId` свидетельствует о сохранённой отмене. Дальше можно сверить её с состоянием заказа и записью возврата.
```

## Состояние заказа и повтор запроса

```case
title: "Проверь результат отмены и составь баг-репорт"
task: >
  Сверься с трейсом из предыдущего блока. Назови два наблюдения в БД,
  которые подтвердят, что операция состоялась. Анна повторяет запрос в 12:00:03Z,
  после истечения окна отмены. Какой ключ она должна отправить и чего ждать?
  Запиши короткий баг-репорт с запросом, ожиданием, фактом, traceId и следующим шагом.
placeholder: "Как проверю БД\nЧто отправит клиент\nКороткий баг-репорт"
reference: |
  В срезе на `11:59:53Z` обнаруживаются обе записи.

  | Источник | Наблюдение |
  | --- | --- |
  | `orders` | `id=42`, `status=CANCELLED`, `cancelled_at=2026-01-16T11:59:52.180Z` |
  | `bonus_transactions` | Одна строка `refund-42` для `order_id=42` с причиной `ORDER_CANCELLED` и суммой `+120` |

  При повторе сервис использует сохранённый результат по ключу `cancel-42-1`. По [контракту](#/m2-order-cancellation-review) он возвращает его даже после истечения окна.

      12:00:03.000Z POST /api/orders/42/cancel Idempotency-Key=cancel-42-1
      12:00:03.019Z orders replay key=cancel-42-1 status=204
      12:00:03.100Z GET /api/orders/42 -> 200 {"id":42,"status":"CANCELLED"}
      12:00:03.130Z bonus_transactions(order_id=42,reason=ORDER_CANCELLED) -> [refund-42]

  Повтор вернул `204`. Заказ остался в `CANCELLED`, и возврат остался один.

  ### Пример баг-репорта

  **После сохранённой отмены браузер получил 504.** Запрос `POST /api/orders/42/cancel` с ключом `cancel-42-1`. Ожидали `204` по завершении операции. Получили `504` при таймауте шлюза. Трейс `42c0a600000000000000000000000001` показывает коммит в `11:59:52.180Z` и готовность ответа в `11:59:54.280Z`. Следующий шаг — проверить, где сервис потратил время между коммитом и подготовкой ответа. Тот же ключ уже вернул `204`. По заказу есть один возврат.
```
