# Урок 3. REST-практики: ресурсы, ошибки, версионирование

Вы умеете описывать контракт. Теперь — правила хорошего тона: как называть ресурсы, как отдавать ошибки и как менять API, не подставляя потребителей. Эти правила не «буква стандарта», а выработанные сообществом привычки — следуя им, вы получаете предсказуемый API, который не надо объяснять каждому новичку.

## Ресурсный дизайн: существительные вместо глаголов

REST строится вокруг **ресурсов** — сущностей, с которыми работают через пути. Путь — «что», HTTP-метод — «что сделать»:

| Хорошо | Плохо | Почему |
|---|---|---|
| `GET /api/tasks` | `GET /api/getAllTasks` | Метод уже говорит «получить» |
| `POST /api/tasks` | `POST /api/createTask` | POST = создать |
| `PATCH /api/tasks/42` | `POST /api/updateTask?id=42` | PATCH = изменить |
| `DELETE /api/tasks/42` | `GET /api/deleteTask?id=42` | DELETE = удалить; GET не меняет! |

Вложенность выражает принадлежность: `/api/projects/7/tasks` — задачи проекта 7. Глубже двух уровней обычно не опускаются.

**А если действие — не CRUD?** Бывают операции вне «создай-измени-удали»: «отправить на проверку», «отменить заказ». Два честных варианта:

- `POST /api/orders/42/cancellations` — создайте «факт отмены» как ресурс (пуристично)
- `POST /api/orders/42/cancel` — глагольный эндпоинт (прагматично, все поймут)

Главное — не прятать смену состояния в GET: «открой ссылку — заказ отменится» — путь к беде (краулеры, префетч браузера).

## Пагинация, фильтрация, сортировка

Списки отдают порциями. Два основных способа:

- **limit/offset**: `GET /api/tasks?limit=20&offset=40` — простые «страницы». Слабость: на живых данных элемент может «уехать» между страницами.
- **cursor**: `GET /api/tasks?limit=20&cursor=eyJpZCI6NDJ9` — «дай следующее после этого». Надёжнее для бесконечных лент, сложнее.

Фильтры и сортировка — query-параметрами: `?status=done&assignee=ann&sort=deadline,asc`. В спеке каждый параметр описан — и потребитель узнаёт о возможностях до первого запроса.

## Единый формат ошибок

Плохой API на каждую ошибку отвечает по-разному. Хороший — в одном формате. Стандарт де-факто — **RFC 7807 Problem Details**:

```json
{
  "type": "https://tasks.example.com/errors/validation",
  "title": "Запрос не прошёл валидацию",
  "status": 400,
  "detail": "title: не должен быть пустым",
  "instance": "/api/projects/7/tasks"
}
```

Поля стабильны: `title` — что случилось (человеком), `detail` — подробности, `type` — ссылка на описание ошибки. В Spring Boot есть встроенная поддержка (ProblemDetail), а для бизнес-ошибок добавляют свой код: `"code": "TASK_ALREADY_DONE"` — по нему фронт принимает решение, а не парсит текст.

Правило: **машина — по коду/статусу, человек — по тексту**. Никогда не завязывайтесь на `detail` как на контракт: это сообщение, оно может измениться.

## Идемпотентность: повторить без страха

Запрос **идемпотентен**, если его повторение не меняет результат сверх первого выполнения:

- `GET`, `PUT`, `DELETE` — идемпотентны (по духу): сколько ни повторяй — состояние то же
- `POST` — нет: два одинаковых POST = два заказа

Проблема: сети падают, клиенты ретраят. Двойной POST «оформить заказ» — двойной платёж. Решения:

- **Идемпотентный ключ**: клиент генерирует `Idempotency-Key: 7f3a...`, сервер запоминает: «этот ключ уже выполнял — верну тот же результат без повторного создания»
- Дизайн API: `PUT /api/orders/{uuid}` (клиент придумал id заранее) вместо `POST /api/orders`

## Версионирование и обратная совместимость

**Обратно совместимое** изменение — старые клиенты продолжают работать:

- добавить новое поле в ответ ✓ (старый клиент его игнорирует)
- добавить новый эндпоинт или необязательный параметр ✓
- удалить поле, переименовать, изменить смысл ✗ (это breaking change)

Breaking changes unavoidable — тогда **новая версия**:

- в пути: `/api/v2/tasks` — просто и наглядно, стандарт де-факто
- в заголовке: `Accept: application/vnd.tasks.v2+json` — чище идеологически, но менее заметен

Уходящая версия не выключается сразу: заголовок `Deprecation`/`Sunset`, письмо потребителям, период параллельной работы версий (месяцы!), мониторинг доли трафика на старой версии — выключаем, когда доля ≈ 0.

> **💡 Фронтендерам:** обратная совместимость — это про ваш спокойный сон. Если бэкенд добавил поле — ваш код не сломается. Если переименовал без версии — упадёт в рантайме, возможно, только в одном rarely-используемом экране. Сгенерированный из спеки клиент ловит такие вещи на этапе компиляции.

> **🔧 QA-инженерам:** проверяйте не только «работает», но и совместимость: старый клиент против нового бэкенда — отдельный класс тестов. Идентичные повторные запросы (идемпотентность) — тоже ваш кейс: ретраи в проде будут.

> **📐 Аналитикам:** deprecation — это управляемое изменение, у которого есть владелец, срок и метрика доли старой версии. Когда просите «убрать поле» — уточняйте план переезда потребителей: это проект, а не коммит.

## Итог

- Ресурсы — существительные; действие — HTTP-метод; смену состояния не прячьте в GET
- Списки — с пагинацией; фильтры и сортировка — query-параметры, описанные в спеке
- Ошибки — единый формат (Problem Details): машина — по статусу и коду, человек — по тексту
- POST не идемпотентен: идемпотентные ключи или клиентские uuid для критичных операций
- Добавлять поля можно, удалять — только через новую версию с периодом deprecation

Следующий урок — GraphQL: стиль API, где клиент сам говорит, какие поля ему нужны.
