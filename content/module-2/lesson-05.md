# Урок 5. Контракт в работе команды

Последний урок модуля — про процесс. Спека сама по себе не спасает: «OpenAPI-файл, который обновляют после кода раз в квартал» — это просто устаревшая документация. Ценность появляется, когда контракт встроен в ежедневную работу всех ролей.

## Жизненный цикл фичи в API-First

Разберём типичную фичу — «просроченные задачи подсвечивать на дашборде»:

**1. Черновик спеки (бэкенд + аналитик).** В `openapi.yaml` появляется изменение: у `TaskResponse` новое вычисляемое поле `overdue: boolean`. Всё обсуждение предметики происходит здесь — на языке полей и типов.

**2. Ревью контракта (все).** PR со спекой смотрят: аналитик — семантика («overdue — это только дата прошла, или ещё и не done?»), фронтендер — достаточно ли полей для UI, QA — описаны ли ошибки. Код ещё не написан — правки бесплатны.

**3. Фиксация версии.** Спека смержена — теперь это договор. Из CI публикуется Swagger UI и генерятся клиенты.

**4. Параллельная работа.**
- Фронтенд: перегенерил TS-клиент, поднял мок-сервер по спеке — верстает дашборд против мока.
- Бэкенд: реализует `overdue` в сервисном слое.
- QA: по спеке готовит тест-кейсы: `overdue=true` при прошедшем дедлайне и `done=false`, `overdue=false` у выполненной, формат даты.

**5. Контрактные тесты.** CI гоняет проверку: живой API соответствует спеке — каждое поле, каждый статус. Расхождение — красный пайплайн, а не «у френта что-то падает».

**6. Релиз.** Фронт переключается с мока на реальный API (или уже жил против тестового стенда). Депрекаций нет — поле новое, обратная совместимость соблюдена.

## Что делает каждая роль

| Роль | Обязанности по контракту |
|---|---|
| **Аналитик** | Семантика полей, сценарии, коды ошибок. Участвует в ревью спеки до кода |
| **Бэкендер** | Пишет и поддерживает спеку, реализует код под контракт, держит контрактные тесты зелёными |
| **Фронтендер** | Читает спеку в Swagger UI, работает против мока, использует сгенерированный клиент, ревьюит изменения на «не сломают ли меня» |
| **QA** | Тест-кейсы и тест-данные из спеки (examples), контрактные тесты как регресс, проверка обратной совместимости и идемпотентности |

Ключевая смена оптики: **обсуждаем контракт — до кода, изменения — через ревью спеки**. Вопрос «а какое поле придёт?» решается не чтением чужого Java-кода, а открытием одного YAML-файла.

## Изменение контракта, который уже в проде

Флоу для изменения живого API:

1. **Предложение**: PR в спеку с пометкой о типе изменения (совместимое / breaking)
2. **Ревью потребителями**: фронт, мобилки, интеграции — «не сломает ли вас»
3. Совместимое — мержим, деплоим, поле появляется. Breaking — новая версия (`/v2`) + `Deprecation`-заголовок старой + план переезда
4. **Changelog**: люди читают changelog, а не diff YAML

## Anti-patterns

- **«Спека потом»** — код уже в проде, спеки нет. Долг растёт с каждым эндпоинтом.
- **«Тихие правки»** — бэкенд поправил поле «по мелочи». Каждый такой раз — лотерея для потребителей.
- **«Спека для галочки»** — файл лежит в репо, генерится из кода раз в квартал, никем не ревьюится.
- **«Диктат бэкенда»** — спека не ревьюится потребителями: «мы знаем лучше». Потом узнают, как выглядели нужные поля, — по багрепортам.
- **«Всё в v1»** — копят breaking changes годами, потом «v2» = переписывание всего. Мелкие версии дешевле больших.

## Экосистема инструментов (шпаргалка)

| Задача | Инструменты |
|---|---|
| Редактирование спеки | Ревью в PR, Swagger Editor, Redoc |
| Просмотр | Swagger UI (попробовать запросы), Redoc (читать) |
| Мок-сервер | Prism, WireMock (по спеке) |
| Генерация | openapi-generator: TS/Java/Python клиенты, заготовки сервера |
| Контрактные тесты | Schemathesis, Dredd, springdoc + Spring тесты |
| Спецификация GraphQL | GraphiQL (песочница), Apollo/Relay на клиенте |

> **📐 Аналитикам:** ваша суперсила в этом процессе — предметная точность. «Поле overdue» без определения — половина багов фичи. Формулировка «задача просрочена, если deadline < сегодня И done = false» в ревью спеки стоит десять минут и экономит неделю споров на тестировании.

> **🔧 QA-инженерам:** контрактные тесты в CI — это «регресс контракта» без ручной работы: любое расхождение кода и спеки краснит пайплайн. А очередь к вам доходит уже с согласованным контрактом и тест-данными — время уходит на настоящее тестирование, а не на выяснение «а что должен возвращать этот эндпоинт».

## Итог

- Контракт ценен процессом: черновик → ревью всеми ролями → версия → параллельная работа → контрактные тесты → changelog
- Фронт не ждёт бэк: мок-сервер и сгенерированный клиент
- Изменения живого API — через PR в спеку; breaking — только новая версия с deprecation
- Anti-patterns: «спека потом», тихие правки, спека для галочки
- У каждой роли в контракте своя зона — и она не «в чужом коде», а в общем YAML

Модуль пройден: вы умеете читать и писать OpenAPI, знаете REST-практики и GraphQL, и понимаете, как контракт живёт в команде. Экзамен и кейс — впереди.
