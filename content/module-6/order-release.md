# Проверка релиза на стенде

Команда выпускает отмену заказа. Твоя задача — сверить, какая сборка отвечает на стенде, найти результат миграции и проверить фичу по [контракту](#/m2-order-cancellation-review). В журналах используются учебные версии и время UTC.

## Сборка прошла проверки

```text
16 января 11:32:00Z CI commit=31dc8a2
  unit              passed
  integration       passed
  openapi-contract  passed
  image             orders:31dc8a2
```

На стенде сначала получаем такой ответ.

```http
GET /version

HTTP/1.1 200 OK
Content-Type: application/json

{"environment":"staging","commit":"7be40f1"}
```

Запрос владельца к `POST /api/orders/42/cancel` в этот момент вернул `404 ROUTE_NOT_FOUND`. Сохрани оба наблюдения перед тем, как открывать баг.

## Стенд после выкладки

```text
11:37:12Z deploy   target=staging image=orders:31dc8a2
11:37:20Z migrate  changeset=2026-01-add-order-cancelled-at result=APPLIED
11:37:36Z rollout  ready=2/2
11:37:40Z version  environment=staging commit=31dc8a2
```

Последняя строка показывает результат повторного `GET /version`. Миграция добавила nullable-колонку `orders.cancelled_at`. Отмена записывает в неё время и меняет статус заказа на `CANCELLED`.

Команда отдельно запустила проверку старого образа на копии данных после миграции.

```text
compatibility image=orders:7be40f1 changeset=2026-01-add-order-cancelled-at
  startup                  PASS
  read order status=NEW    PASS
  read order status=CANCELLED FAIL unknown OrderStatus CANCELLED
```

```case
title: "Проверь выкладку и подготовь решение об откате"
task: >
  Назови версию на стенде до и после выкладки. По какой строке видно,
  что миграция применилась? Как проверишь отмену после выкладки?
  Составь краткий план для прав, границы 24 часов, двух видов повтора и записей в БД.
  Оцени возможность вернуть старый образ по результатам проверки совместимости.
placeholder: "Версии и миграция\nЗапрос после выкладки\nПроверки контракта\nРешение об откате"
reference: |
  В CI собран образ `31dc8a2`. Первый ответ стенда показывает `7be40f1`, где маршрут отмены ещё отсутствует. После выкладки запрос версии показывает `31dc8a2`, а журнал отмечает `2026-01-add-order-cancelled-at` как `APPLIED`. Эти свидетельства дают версия и журнал окружения.

  Для быстрой проверки подготовь исходный заказ `42` в тестовой копии данных. Отправь `POST /api/orders/42/cancel` как владелец в пределах окна, с новым `Idempotency-Key`. Ожидай `204`. Потом прочитай заказ через `GET /api/orders/42` и проверь статус `CANCELLED` и единственный возврат в журнале бонусов.

  | Проверка | Ожидаемый результат |
  | --- | --- |
  | Анна, Борис и запрос без токена | Владелец может отменить свой заказ. У Бориса `403`, без токена `401` |
  | Три исходных заказа на отметках `11:59:59Z`, `12:00:00Z` и `12:00:01Z` | Перед границей `204`. На границе и после неё `409 CANCELLATION_WINDOW_EXPIRED` |
  | Тот же ключ после успешной отмены | `204` и одна строка возврата |
  | Другой ключ после успешной отмены | `409 ORDER_ALREADY_CANCELLED` и та же строка возврата |
  | Проверка данных после успеха | `CANCELLED`, заполненный `cancelled_at` и возврат по `order_id` с причиной `ORDER_CANCELLED` |

  **Откат.** Старый образ запускается на новой схеме и читает `NEW`. Проверка строки с `CANCELLED` падает. Это конкретный блокер для возврата старого образа поверх этих данных. Перед откатом нужен образ, который читает все уже записанные состояния, и проверка чтения и записи на копии с применённой миграцией.
```

## Совместимость клиента при новом статусе

В следующем учебном релизе тот же `GET /api/orders/42` может вернуть `PAYMENT_PENDING`, пока заказ ждёт подтверждения оплаты. Поле `status` использует `enum`, который задаёт допустимые значения в схеме ответа. [Перечисления в JSON Schema](https://json-schema.org/understanding-json-schema/reference/enum)

```diff
 status:
   type: string
-  enum: [NEW, CANCELLED]
+  enum: [NEW, CANCELLED, PAYMENT_PENDING]
```

Упражнение показывает карточку владельца в пределах окна отмены. Кнопка отмены активна в `NEW` и отключена в `CANCELLED` и `PAYMENT_PENDING`.

1. Выбери ответ API 1.9 со статусом `PAYMENT_PENDING` и клиент 1.4. Запиши HTTP-статус и результат открытия карточки.
2. Прогони проверки клиента 1.4. Найди сценарий, на котором он падает.
3. Переключись на клиент 1.5. Сверь результат для нового статуса и двух прежних.

```order-compatibility
```

Новый статус включается на сервере по флагу. После выкладки обновления в браузерах могут оставаться открытые вкладки с клиентом 1.4.

```case
title: "Согласуй порядок выкладки"
task: >

  на которых карточка сломалась. Запиши проверку с ожидаемой подписью и
  состоянием кнопки. Объясни смысл PAYMENT_PENDING. В каком порядке
  выкатишь клиент и включишь статус? Как учтёшь открытые старые вкладки?
placeholder: "Воспроизведение\nПроверка для QA\nСмысл статуса\nПорядок выкладки и условие включения"
reference: |
  **Фронтенд.** API 1.9 вернул `200` и `"status": "PAYMENT_PENDING"`. Клиент 1.4 получил незнакомое значение и прервал отрисовку карточки. Для исправления проверь и чтение ответа клиентской библиотекой, и отображение карточки.

  **QA.** На ответе с `PAYMENT_PENDING` ожидай «Ожидает подтверждения оплаты» и отключённую кнопку отмены. У клиента 1.4 эта проверка падает. У клиента 1.5 проходят проверки нового статуса, `NEW` и `CANCELLED`.

  **Аналитик.** `PAYMENT_PENDING` означает, что заказ ждёт подтверждения оплаты. В карточке владельца на этом этапе видно ожидание, а действие отмены отключено. Запиши новое значение и его смысл в контракте.

  **Выкладка.** Сначала проверь и выложи клиент 1.5 поверх API 1.8. Дождись обновления поддерживаемых клиентов, включая старые открытые вкладки. Затем включи флаг на стенде и прогони три проверки. В критерий включения в прод добавь подтверждение, что новый ответ получат только совместимые клиенты. Отдельно проверь выключение флага на заказе, у которого уже записан `PAYMENT_PENDING`.
```
