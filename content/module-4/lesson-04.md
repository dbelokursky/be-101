# Урок 4. Консюмер и группы

Вторая сторона диалога: кто и как читает лог. Разберём группы и ребалансировку — механику, которая раскидывает партиции по инстансам, — и главное: где живут повторы, пропуски и мёртвые сообщения.

## Consumer group: очередь внутри pub/sub

Группа превращает topic в очередь **для себя**: партиции topic'а делятся между инстансами группы, каждое событие достаётся ровно одному инстансу группы. Разные группы друг другу не мешают — каждая читает всё.

```text
topic (3 партиции), группа mail-service из 3 инстансов:

  partition 0 → инстанс-1
  partition 1 → инстанс-2
  partition 2 → инстанс-3

группа analytics читает те же партиции СВОИМИ силами и со своими offset'ами
```

Масштабирование: медленно обрабатываете — добавляете инстансы (до числа партиций). Отказоустойчивость: инстанс умер — его партиции перераспределятся.

## Rebalance: перетасовка партиций

Изменение состава группы (упал/поднялся инстанс, деплой) → **rebalance**: партиции заново делят между выжившими. На время ребаланса группа стоит: не паникуйте, это секунды. Тонкость — что считать «умершим»: `max.poll.interval.ms` — если обработка батча дольше, консюмер выкидывается из группы, инициируя ребаланс. Медленный обработчик → вечные ребалансы → группа буксует. Лечение: батчи меньше, обработка быстрее, тяжёлое — наружу из листенера.

## Обработка, потом коммит

Цикл консюмера: прочитать батч → обработать → **заккоммитить offset'ы**. Момент коммита определяет семантику сбоя:

| Коммит | Сбой после | Последствие |
|---|---|---|
| После обработки | Коммита | Событие обработается повторно (**дубль**) |
| До обработки | Коммита | Событие потеряно (**пропуск**) |

Spring-листенер коммитит после успешного вызова метода: потерь не получится, дубли — могут (норма at-least-once, урок 1). Отсюда железное требование идемпотентности обработчика.

## Ошибки обработки: DLT

Обработчик упал на «ядовитом» сообщении (битый JSON, неожиданное состояние). Без стратегии — бесконечный цикл: партиция стоит, событие возвращается после рестарта. Штатное решение — **Dead Letter Topic (DLT)**: после N безуспешных попыток событие уезжает в `topic.DLT`, партиция продолжает жить:

```java
@KafkaListener(
        topics = "orders.created",
        groupId = "mail-service",
        properties = {"default.deserialization.value..."}, // опустим
        ...)
@RetryableTopic(attempts = "4", dltTopicSuffix = ".DLT")   // 3 попытки, потом .DLT
public void onOrderCreated(OrderCreatedEvent event) {
    mailService.sendOrderConfirmation(event.orderId());
}

@DltHandler
public void toDlt(OrderCreatedEvent event) {
    log.error("Событие ушло в DLT после ретраев: {}", event);
    // алерт, разбор руками, починка и переигровка
}
```

DLT — не мусорка, а рабочий инструмент: алерт на его глубину, регулярный разбор, переигрывание после починки.

## @KafkaListener: что ещё в хозяйстве

- **Фильтры**: пропускать нецелевые события до обработчика
- **Батчи**: слушать `List<Message<?>>` — для высоких потоков
- **Заголовки**: трейсинг-id, версия схемы — читаются как метаданные
- **Ручной Ack**: точный контроль коммита для «обработал пачку — закоммитил разом»

> **🔧 QA:** три обязательных кейса по консюмерам: (1) дубль — событие пришло дважды, эффект один; (2) яд — битое сообщение не подвешивает партицию, а уезжает в DLT; (3) ребаланс — убийство инстанса не теряет события. Если фича проходит все три — она переживёт пятничный деплой.

> **📐 Аналитикам:** «событие не обработалось» — теперь измеримый процесс: N попыток → DLT → алерт. Требование «все заказы получают письма» превращается в метрику «глубина DLT = 0 и лаг группы = 0». Это ваш язык с инженерами.

## Итог

- Группа делит партиции между инстансами: каждая группа читает всё своими темпами
- Rebalance перетасовывает партиции при изменении состава; долгая обработка → выпадение из группы
- Коммит после обработки: терять нельзя, дубли можно (идемпотентность!)
- Ядовитые события — в DLT после N попыток: партиция живёт, инцидент виден
- Лаг группы (отставание от хвоста лога) — главная метрика здоровья консюмера

Последний урок модуля собирает надёжность в целые паттерны: outbox, идемпотентный консюмер и порядок vs параллелизм.
