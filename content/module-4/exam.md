# Экзамен модуля «Kafka вглубь»

Брокер, партиции, продюсеры, группы, надёжность — всё в одном финале: кейс, затем 15 вопросов, порог 80%.

## Кейс

```case
title: "Спроектируй события для интернет-магазина"
task: "Магазин: заказы, платежи, склад, письма, аналитика. События уже частично есть: orders.created. Опишите: (1) какие ещё события нужны и как их назвать (домен.факт); (2) ключ каждого события и почему; (3) кто консюмеры и их группы; (4) какие события требуют outbox и строгой идемпотентности, а какие живут по-проще; (5) что делать, если 'payments.succeeded' иногда приходит дважды. Форма свободная."
placeholder: "Например:\norders.created — ключ orderId...\nmail-service (группа) читает ...\noutbox нужен для ..."
reference: |
  Один из возможных ответов.

  ## События и ключи

  | Событие | Ключ | Почему ключ |
  |---|---|---|
  | `orders.created` | orderId | Порядок событий заказа |
  | `orders.cancelled` | orderId | Тот же ключ — та же партиция, порядок с created |
  | `payments.succeeded` / `payments.failed` | orderId (или paymentId + версия) | Обработка в порядке судьбы заказа |
  | `stock.reserved` / `stock.unavailable` | orderId | Резерв под конкретный заказ |
  | `users.registered` | userId | Порядок событий пользователя |

  Правило: ключ = сущность, чьи события обязаны идти по порядку. Имя = домен.факт.

  ## Консюмеры и группы

  - `mail-service` (группа) — orders.created/cancelled: письма
  - `analytics` (группа) — всё: дашборды. Свои offset'ы, свой темп
  - `stock-service` (группа) — payments.succeeded: списание резерва
  - `search-indexer` (группа) — orders.*, users.*: обновление поиска

  Разные группы читают одни и те же топики независимо — каждый со своей закладкой.

  ## Уровни надёжности

  | Событие | Подход |
  |---|---|
  | orders.created | acks=all + **outbox** (заказ без события — баг интеграции) + идемпотентная обработка |
  | payments.* | acks=all + outbox + **строгая идемпотентность** (деньги) |
  | аналитические клики/просмотры | at-most/at-least, дубли терпимы — без церемоний |

  ## Дубли payments.succeeded

  At-least-once: повторы — норма доставки. Защита на стороне эффекта:
  - зачисление/списание — UPDATE по бизнес-ключу с естественной идемпотентностью (`WHERE status = 'PENDING'`);
  - таблица processed_events(eventId) в одной транзакции с эффектом;
  - версии событий для устаревших.

  Итог: effectively-once = at-least-once + идемпотентный обработчик.

  ## Бонус: заказ без события (dual-write)

  Если публикация идёт из транзакции создания заказа — возможен заказ-призрак. Outbox: заказ + outbox_event одной транзакцией, релей публикует. 
```
