# Урок 3. Продюсер: публикация без потерь

Продюсер выглядит как одна строка `kafkaTemplate.send(...)` — пока всё хорошо. Урок о том, что за этой строкой: сериализация, ключи, подтверждения и что отличает «отправил» от «не потерял».

## Анатомия send()

```java
kafkaTemplate.send("orders.created", "42", new OrderCreatedEvent(42L, amount));
//              topic               ключ      значение (payload)
```

Путь сообщения внутри продюсера:

1. **Сериализация**: ключ и значение превращаются в байты — `StringSerializer`, `JsonSerializer` (вес события — обычный JSON)
2. **Партиционирование**: хэш ключа → номер партиции; без ключа — round-robin/sticky
3. **Батчер**: сообщения копятся микробатчами (за счёт этого Kafka такая быстрая)
4. **Отправка + ожидание подтверждения** — по настройке `acks`

## acks: кто и перед кем отчитывается

| acks | Подтверждение | Риск |
|---|---|---|
| `0` | Не ждём никого | Пожар: могло не дойти вообще |
| `1` | Лидер партиции записал | Лидер упал до репликации — событие потеряно |
| `all` | Все ISR-реплики записали | Надёжно; стандарт для ценных данных |

`acks=all` — правильный дефолт для доменных событий. Дешевле всего терять логи метрик (`acks=1`), дороже всего — деньги.

Идемпотентный продюсер (`enable.idempotence=true`, в свежих версиях включён по умолчанию): брокер помнит «продюсер №X уже писал с seq №Y» и отбрасывает повтор — ретраи сети не плодят дубли **на стороне записи**.

## Ретраи и таймауты

Сеть мигает — продюсер ретраит сам (`delivery.timeout.ms`, `retries`). Правило: **ретраи без идемпотентности = дубли**, поэтому идемпотентность и ретраи ходят парой. Исчерпал попытки — `send` завершится исключением: ловите и решайте, что важнее — потерять событие или уронить операцию.

## Отправка из транзакции: проблема dual-write

Классическая ловушка (мы её почти вырыли в уроке 1):

```java
@Transactional
public void create(...) {
    orderRepository.save(order);                    // ① запись в БД
    kafkaTemplate.send("orders.created", event);    // ② отправка в Kafka
}
```

Коммит БД происходит **после** выхода из метода. Упало между ② и коммитом? Событие о **несуществующем** заказе. Упало после коммита, но ① без ② (брокер недоступен)? Заказ есть — события нет, аналитика никогда не узнает. Это **dual-write problem**: две независимые системы записи без общей транзакции.

Штатное решение — **transactional outbox** (детали в уроке 5): в той же БД-транзакции пишем событие в таблицу `outbox`, отдельный релей читает её и публикует в Kafka. Запись заказа и «намерение опубликовать» становятся атомарными.

> **💡 Фронтендерам:** dual-write — старый знакомый: «сохрани на сервере и отправь аналитику» в двух вызовах из браузера роняется точно так же. Outbox — «сначала записал в один источник, потом разнёс» — тот же паттерн, что оптимистичные обновления UI.

## Практика конфигурации

```yaml
spring:
  kafka:
    producer:
      acks: all
      properties:
        enable.idempotence: true
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
```

Именование topic'ов — контракт: `домен.факт` (`orders.created`, `payments.succeeded`). Не `events`, не `topic1`: по имени должно быть понятно, что случилось.

## Итог

- Путь события: сериализация → партиция по ключу → батч → подтверждение
- `acks=all` + идемпотентный продюсер — норма для доменных событий; acks=0/1 — осознанный риск
- Ретраи безопасны только с идемпотентностью записи
- Dual-write (БД + Kafka в одном методе) — источник потерянных/фантомных событий; лечится outbox-паттерном
- Имя topic'а — часть контракта: `домен.факт`, ключ — идентичность сущности

Следующий урок — вторая сторона: консюмеры, группы и что происходит при сбоях чтения.
