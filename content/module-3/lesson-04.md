# Урок 4. Транзакции и изоляция

`@Transactional` в пилоте был заклинанием «всё или ничего». Теперь — что это значит на самом деле: ACID, уровни изоляции, аномалии гонок и блокировки. Это урок про то, что происходит, когда два пользователя жмут кнопку одновременно.

## ACID: четыре обещания транзакции

**Атомарность** — всё или ничего: упало на середине — откат целиком.
**Согласованность** — данные переходят из одного корректного состояния в другое: инварианты (сумма списания = сумме зачисления) не нарушаются.
**Изоляция** — параллельные транзакции не видят чужие полусырые изменения.
**Долговечность** — commit записан — переживёт перезагрузку сервера.

Spring-разработчик чаще всего сталкивается с А (откат) и I (гонки). Ими и займёмся.

## @Transactional: границы — это и есть смысл

Транзакцию открывает **первый** запрос к базе внутри метода и закрывает коммит/откат на выходе:

```java
@Transactional
public void transfer(Long from, Long to, BigDecimal amount) {
    accountRepository.withdraw(from, amount);   // BEGIN
    if (кредитный лимит нарушен) {
        throw new IllegalStateException(...);   // ROLLBACK: списание отменено
    }
    accountRepository.deposit(to, amount);      // COMMIT на выходе
}
```

Правила, которые экономят часы дебага:

- **Только публичные методы** через прокси — вызов `this.transfer(...)` из другого метода того же класса транзакции **не откроет** (вызов мимо прокси)
- Исключение **unchecked** (RuntimeException) → откат; **checked** → по умолчанию коммит (сюрприз! настраивается `rollbackFor`)
- `readOnly = true` — «только чтение»: БД и Hibernate могут оптимизировать; вешайте на выборки
- Транзакция должна быть **короткой**: внутри не делают HTTP-вызовы и не спят — соединение с базой занято

## Гонки: два одинаковых запроса одновременно

Изоляция по умолчанию в PostgreSQL — READ COMMITTED: транзакция видит закоммиченные чужие изменения. Это быстро, но порождает гонки:

**Потерянный подсчёт.** Остаток товара = 1. Два покупателя жмут «купить» одновременно:

```text
T1: читает остаток = 1      T2: читает остаток = 1
T1: остаток = 0, commit     T2: остаток = 0, commit
```

Обе транзакции прошли, продан один товар — а купили два. READ COMMITTED не спас: каждая видела согласованную картину.

**Решение 1 — пессимистичная блокировка**: «захватить строку себе»:

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select i from Item i where i.id = :id")
Optional<Item> findByIdForUpdate(@Param("id") Long id);
```

Первый читатель блокирует строку: второй ждёт. `SELECT ... FOR UPDATE` — надёжно, но очередь при горячих строках.

**Решение 2 — оптимистичная блокировка**: версия вместо блокировки:

```java
@Version
private Long version;   // Hibernate: UPDATE ... WHERE id=? AND version=?
```

Обе транзакции читают версию 5; первая коммитит (версия → 6); вторая при UPDATE «не нашла» свою версию → `OptimisticLockException` → повторить. Не держит блокировки, идеальна для UI-конфликтов («данные изменил другой пользователь»).

**Решение 3 — атомарный UPDATE**, когда результат не зависит от прочитанного:

```java
@Modifying @Query("update Item i set i.qty = i.qty - 1 where i.id = :id and i.qty > 0")
int tryDecrement(@Param("id") Long id);   // вернёт 0, если не вышло
```

База сама гарантирует: ровно одна параллельная транзакция успеет. Часто это самый простой и честный путь.

## Уровни изоляции (шпаргалка)

| Уровень | Аномалии | Комментарий |
|---|---|---|
| READ UNCOMMITTED | грязное чтение | почти не используется |
| READ COMMITTED | неповторяемое чтение, фантомы | **дефолто Postgres** |
| REPEATABLE READ | фантомы | дефолт MySQL |
| SERIALIZABLE | — | как последовательное выполнение; медленно |

Аномалии: **грязное чтение** — чужие незакоммиченные данные; **неповторяемое чтение** — два чтения одной строки дают разное; **фантомы** — повторный запрос возвращает другой набор строк.

Поднимать уровень изоляции «на всякий случай» — антипаттерн: каждый уровень дороже. Правильный инструмент под конкретную гонку: блокировка, версия или атомарный UPDATE.

## Распространённые ошибки

- Транзакция ради транзакции на каждом методе — пул соединений кончается
- HTTP-вызов внутри транзакции — соединение занято на секунды
- `@Transactional` на private методе или внутреннем вызове — молча не работает
- Решение гонок сном (`Thread.sleep(100)`) — «иногда помогает» — нет
- Долгая транзакция на «импорт файла на 100к строк» — держит блокировки; батчами и короткими транзакциями

> **🔧 QA:** гонки не ловятся одиночным тестом — ловятся параллельными: два потока одновременно на один остаток, повторные отправки формы, двойной клик по кнопке. «Задвоение данных при двойном клике» — самый частый прод-тикет из этой серии.

## Итог

- ACID; на практике ломаются А (откат) и I (гонки)
- `@Transactional`: границы = метод, публичный вызов через прокси, unchecked → откат, короткая жизнь
- READ COMMITTED (дефолт PG) не защищает от гонок чтение-запись
- Инструменты: пессимистичная блокировка (ждать), `@Version` (повторить), атомарный UPDATE (база сама)
- Уровни изоляции не «на всякий случай», а под конкретную аномалию
