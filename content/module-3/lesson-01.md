# Урок 1. Реляционная база и SQL-минимум

До сих пор база была «чёрным ящиком»: репозиторий сам что-то делал. Модуль — про то, что внутри: таблицы, ключи, запросы, транзакции. Половина бэкенд-багов — это SQL-проблемы, надетые на Java. Начнём с фундамента — реляционной модели.

> **📐 Аналитики:** этот урок — ваша территория: вы давно живёте в таблицах и JOIN'ах. Задача — освежить термины, потому что дальше весь модуль говорит на этом языке. А вот уроки 2–3 покажут вам, во что превращаются ваши таблицы в Java-кодe.

## Таблицы, строки, колонки

Реляционная база — набор **таблиц**. У таблицы фиксированные **колонки** (типизированные) и любое количество **строк**:

```sql
CREATE TABLE tasks (
    id          BIGINT PRIMARY KEY,
    project_id  BIGINT NOT NULL,
    title       VARCHAR(200) NOT NULL,
    done        BOOLEAN NOT NULL DEFAULT FALSE,
    deadline    DATE
);
```

- **PRIMARY KEY** — первичный ключ: значение, однозначно идентифицирующее строку. У нас — `id`.
- **NOT NULL** — поле обязательно.
- **DEFAULT** — значение по умолчанию.

## Связи: внешний ключ

Таблицы связываются **внешним ключом** (FOREIGN KEY): колонка в одной таблице указывает на первичный ключ другой:

```sql
CREATE TABLE projects (
    id   BIGINT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

ALTER TABLE tasks
    ADD CONSTRAINT fk_tasks_project
    FOREIGN KEY (project_id) REFERENCES projects (id);
```

Теперь `tasks.project_id` обязан существовать в `projects.id` — база не даст записать задачу «в никуда». Это **ссылочная целостность**: база охраняет связи, а не полагается на аккуратность кода.

Виды связей, которые встречаются постоянно:

| Связь | Пример | Как выражена |
|---|---|---|
| один-ко-многим | проект → задачи | FK на стороне «многих» (`tasks.project_id`) |
| один-к-одному | пользователь → паспорт | FK + уникальность |
| многие-ко-многим | задачи ↔ исполнители | отдельная таблица-связка `task_assignees(task_id, user_id)` |

## SQL: четыре главных глагола

```sql
-- прочитать
SELECT id, title, done FROM tasks WHERE done = false ORDER BY deadline;

-- вставить
INSERT INTO tasks (project_id, title, done) VALUES (7, 'Купить молоко', false);

-- изменить
UPDATE tasks SET done = true WHERE id = 42;

-- удалить
DELETE FROM tasks WHERE id = 42;
```

Джойн — соединение таблиц по связи:

```sql
SELECT p.name AS project, t.title
FROM tasks t
JOIN projects p ON p.id = t.project_id
WHERE t.done = false;
```

Читается: возьми задачи, к каждой приклей её проект по `project_id = id`, оставь несделанные.

Агрегация — когда нужен не список, а число:

```sql
SELECT p.name, COUNT(*) AS open_tasks
FROM tasks t
JOIN projects p ON p.id = t.project_id
WHERE t.done = false
GROUP BY p.name
HAVING COUNT(*) > 5
ORDER BY open_tasks DESC;
```

## Индексы: почему одни запросы быстрые, а другие — вечные

Без индекса `WHERE title = '...'` — **полный перебор** всех строк (full scan). Индекс — отсортированная структура (B-дерево) по колонке: поиск по ней — логарифмический, как в оглавлении книги.

```sql
CREATE INDEX idx_tasks_project ON tasks (project_id);
```

Правила выживания:

- PK и FK индексируются (FK не всегда автоматически — зависит от БД, проверяйте)
- Индекс ускоряет `WHERE`, `JOIN`, `ORDER BY` по этой колонке
- Индекс не бесплатен: каждый INSERT/UPDATE чуть медленнее, индексы занимают место
- «Запрос внезапно стал медленным» — почти всегда «данные выросли, а индекса нет»

> **🔧 QA:** если фича «тормозит на проде, а локально мгновенно» — классика: локально 100 строк (перебор незаметен), на проде 10 миллионов. Спросите про индекс и план запроса (EXPLAIN) — звучите как король багрэйтов.

## Из Java это видно как…

Всё, что вы узнали, напрямую отражается в коде:

| В базе | В Java (Spring) |
|---|---|
| Таблица `tasks` | entity-класс `Task` с `@Entity` |
| Колонка `title` | поле `title` |
| PK `id` | `@Id @GeneratedValue` |
| FK `project_id` | поле связи `@ManyToOne Project project` |
| `SELECT ... WHERE done=false` | `findByDone(false)` репозитория |
| Индекс | `@Table(indexes = @Index(...))` или миграция |

Подробно это соответствие — урок 2. А пока зафиксируем язык.

## Итог

- Таблицы + строки/колонки; PK — идентичность строки, FK — связь и ссылочная целостность
- Связи: один-ко-многим через FK у «многих», многие-ко-многим — через таблицу-связку
- SQL: SELECT/INSERT/UPDATE/DELETE + JOIN + GROUP BY
- Индексы ускоряют поиск по колонке, но стоят при записи; full scan на больших данных — источник «внезапных» тормозов
