# Доступ к API

Для заказа `42` сервис сначала устанавливает, кто отправил запрос. Затем проверяет, разрешено ли этому пользователю читать этот заказ.

## Как API узнаёт пользователя

**Аутентификация** устанавливает личность. При входе сервер может создать сессию и выдать браузеру cookie с её идентификатором. Браузер прикладывает подходящую cookie к запросам, и сервер находит сессию. Другой распространённый вариант — клиент передаёт токен в заголовке `Authorization: Bearer …`.

**Авторизация** проверяет разрешение на действие. Правила могут учитывать роль пользователя и связь с объектом. В учебном API у Анны и Бориса есть действительные токены. Заказ `42` доступен его владельцу Анне.

При `401` проверь, пришли ли действительные учётные данные. Для защищённого API с Bearer-токеном ответ на недействительный токен обычно содержит `401` и заголовок `WWW-Authenticate`. При `403` смотри правило доступа. API также может использовать `404`, чтобы скрыть существование закрытого ресурса. [Использование Bearer-токенов](https://www.rfc-editor.org/rfc/rfc6750.html#section-3) · [Статусы HTTP](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4)

## Когда браузер блокирует ответ

Origin складывается из схемы, хоста и порта. Страница `https://app.shop.example.test` и API `https://api.shop.example.test` имеют разные origin. Браузер проверяет CORS, чтобы определить, может ли код страницы прочитать ответ API.

В первом учебном фрагменте **Network** страница вызвала `fetch` с `credentials: 'include'`. Браузер отправил подходящую cookie. Сервис нашёл сессию и ответил `200`. Без заголовка `Access-Control-Allow-Origin` браузер заблокировал чтение ответа скриптом страницы.

```http
GET /api/orders/42 HTTP/1.1
Host: api.shop.example.test
Origin: https://app.shop.example.test
Cookie: session=demo

HTTP/1.1 200 OK
Content-Type: application/json
```

В другом фрагменте браузер сначала отправил **preflight**. Для запроса отмены с `Authorization` и `Idempotency-Key` он спросил у API, допустим ли такой вызов с указанного origin. После отказа на `OPTIONS` браузер завершил запрос до отправки `POST`.

```http
OPTIONS /api/orders/42/cancel HTTP/1.1
Host: api.shop.example.test
Origin: https://app.shop.example.test
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization,idempotency-key

HTTP/1.1 403 Forbidden
```

При разборе такого сбоя сначала найди в Network метод запроса, получившего отказ. Если видишь `OPTIONS`, проверь origin и разрешения для метода и заголовков. Если видишь `403` у уже отправленного `POST`, посмотри ответ API и правила доступа к ресурсу. [Проверки CORS в Fetch Standard](https://fetch.spec.whatwg.org/#http-fetch)
