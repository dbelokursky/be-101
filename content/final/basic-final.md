# Бронирование после таймаута

Нина бронирует переговорку `R-204`. После подтверждения формы браузер получает `504`. Твоя задача — выяснить судьбу брони и описать безопасный повтор. Запрос, журнал и срез БД взяты из учебного сценария.

## Контракт бронирования

| Условие | Ответ на `POST /api/bookings` |
| --- | --- |
| Свободный слот, новый ключ операции | `201 Created`, `Location: /api/bookings/{id}` и JSON с идентификатором и состоянием брони |
| Тот же пользователь, ключ и тело в течение 24 часов после успешного коммита | Сохранённые статус, `Location` и тело исходного ответа |
| Тот же пользователь и ключ, тело изменилось | `409 IDEMPOTENCY_KEY_REUSED` |
| Новый ключ, этот слот уже занят | `409 SLOT_TAKEN` |

Успешное бронирование и ответ для повторного запроса сохраняются одной транзакцией. Сервис определяет пользователя по токену.

## Запрос и свидетельства

В журнале шлюза сохранён запрос Нины.

```http
POST /api/bookings HTTP/1.1
Host: booking.example.test
Authorization: Bearer TOKEN-NINA
Content-Type: application/json
Idempotency-Key: r204-reserve-7

{"roomId":"R-204","startsAt":"2026-02-09T10:00:00Z","endsAt":"2026-02-09T10:30:00Z"}
```

Это строки одного трейса `book-184`.

```text
09:41:00.000Z  bookings  receive principal=nina key=r204-reserve-7
09:41:03.050Z  gateway   response status=504 reason=upstream_timeout
09:41:03.105Z  bookings  commit booking_id=731 status=CONFIRMED response_status=201
```

Срез таблицы `bookings` в 09:41:04Z отфильтрован по комнате и интервалу запроса.

| id | room_id | employee | starts_at | ends_at | status |
| --- | --- | --- | --- | --- | --- |
| 731 | R-204 | nina | 10:00Z | 10:30Z | CONFIRMED |

В срезе хранилища идемпотентности сохранён ответ для пары `nina` и `r204-reserve-7`.

```http
HTTP/1.1 201 Created
Location: /api/bookings/731
Content-Type: application/json

{"id":731,"roomId":"R-204","startsAt":"2026-02-09T10:00:00Z","endsAt":"2026-02-09T10:30:00Z","status":"CONFIRMED"}
```

## Твоё решение

1. Опиши, какой ответ увидела Нина и какой ответ предписывает контракт при повторе того же запроса через минуту.
2. Приведи повторяемый HTTP-запрос с методом, адресом, заголовками и телом.
3. По строкам трейса и срезу БД обоснуй состояние брони и количество записей после повторного запроса.
4. Предложи следующую проверку. Назови входные данные, ожидаемый ответ и состояние БД.

Добавь один результат для своей роли.

- **Фронтенд.** Что показать после `504` и как сохранить идентификатор операции для кнопки повтора.
- **QA.** Как изменить запрос, чтобы проверить конфликт ключа, и что сверить в БД.
- **Аналитик.** По каким полям найти исходную бронь и как отличить повторный ответ API от создания второй записи.
